# Prediction Model Follow-up Audit — Commit `11857ec`

## Overall result

The new commit is a **substantive improvement** and addresses much of the first audit. It is no longer accurate to say that the repository only has same-timestamp synthetic targets or that the code lacks any chronology, gauge masking, artifact, or metric-provenance work.

However, the prediction system is **still not ready for production flood-warning use**. The primary remaining problem is that the published `validation_scorecard.json` is generated by a validator that does not use the new future-window dataset pipeline. It reads individual current weather rows, feeds them one at a time into the standalone model, and compares predictions to precipitation on those same rows. The new dataset builder is substantially better, but the headline scorecard is still not an end-to-end future-forecast evaluation of it.

## Remaining findings

### Critical — the published scorecard still is not future-forecast validation

`validate.py` loads weather rows into `test_samples` and sets `rain_target` from the precipitation value on that same row. It then performs one recurrent step and compares the output with that row's label. There is no 24-hour input window, no target timestamp at `t0+h`, and no use of `TelemetryDataset(split="test", horizon=...)`.

This means the new future-window logic in `dataset.py` is not what produced the committed `validation_scorecard.json`. The scorecard's improved metric fields therefore do not establish future forecast performance for MF-1 or MF-2.

**Required correction:** make the validator consume the exact chronological test windows produced by the canonical dataset builder. For each sample, record `forecast_origin_timestamp`, `target_timestamp`, station ID, and horizon. Validate predictions only against the target at that future timestamp.

### Critical — validator recurrent state crosses station boundaries

The validator initializes `h` once before iterating over all records and never resets it when `st_id` changes. The weather CSV is not guaranteed to be globally ordered by station and time, and the model's hidden state therefore carries information from one station into another.

The revised dataset loader correctly isolates station windows, but the published validator does not.

**Required correction:** reset hidden state at every station boundary and process each station chronologically. Prefer batch/window inference from the canonical test dataset rather than row-wise streaming over the CSV.

### Critical — the committed dataset contains a timestamp outlier

The updated weather file contains two records for station `nDbyYbR1` dated in **2069**, while the rest of the data is in 2026. The exact global range is approximately June–August 2026 plus those 2069 records. The new loader sorts timestamps, so the outliers are moved to the end of that station's series and enter the test region.

This can contaminate chronology, split boundaries, forecast gaps, and any future performance report. It also makes the data manifest internally inconsistent with the apparent collection period.

**Required correction:** reject or quarantine timestamps outside the declared collection range, document the data-quality rule, recompute hashes and all artifacts, and assert that no timestamp is outside the expected period.

### High — the new MF-1 training script has no true untouched test evaluation

`train.py` trains on `split="train"` and reports validation on `split="val"`, but the committed PyTorch checkpoint metadata records only the best validation loss. The repository does not show a final MF-1 test scorecard produced from `split="test"` at the requested forecast horizon.

The dataset builder supports `test`, but support in the loader is not equivalent to a reported untouched test result.

**Required correction:** keep the test period inaccessible during model selection, run a separate test command after training, and publish metrics for MF-1 by horizon and station.

### High — normalization is documented as train-fitted but remains hard-coded in the main path

`dataset.py` still defines fixed `FEATURE_MEANS` and `FEATURE_STDS`, and `train.py` constructs the train and validation datasets without passing fitted training statistics. The checkpoint manifest records these constants, but the code does not fit them on the training split.

This is reproducible, but it is not the claimed “fit on training data only” preprocessing protocol and can leak distribution information if those constants were calculated from the complete historical corpus.

**Required correction:** calculate means and standard deviations from the training split only, pass them into validation/test builders, and save them in the checkpoint.

### High — the water-level metric is real but operationally limited

The new scorecard correctly reports real gauge observations and explicitly says they come from one gauge. That is a major improvement. But the committed result is approximately **0.6199 m MAE / 0.676 m RMSE over 911 gauge-matched samples**, which is poor for a flood-stage warning model unless the acceptable error tolerance is explicitly much larger.

The metric is also produced by the standalone validator rather than the PyTorch canonical model, and the scorecard does not provide a persistence baseline for comparison.

**Required correction:** report MF-1 and MF-2 separately, compare both with persistence and a simple rainfall/runoff baseline, and show errors by forecast horizon and rising-stage event.

### High — conformal coverage is calibration-set coverage, not independent test coverage

The validator computes quantiles and then verifies empirical coverage on the same residual collection used to calculate the bands. The reported 80.1%, 90.1%, and 95.2% values therefore demonstrate in-sample calibration-set coverage, not independent coverage on a separate future test period.

**Required correction:** fit conformal bands on a calibration period and report coverage on a distinct test period, preferably by horizon and event regime.

### Medium — forecast horizon semantics remain mixed in inference

`inference.py` now clearly discloses that it creates projected, not observed, input sequences. This is good safety communication. Nevertheless, the API still returns a `lead_horizon` such as `24h` while the model receives a fabricated 24-step sequence and outputs each step. The README correctly says this is not a validated 24-hour accuracy claim, but the interface remains easy to misinterpret.

**Required correction:** expose two separate APIs: one for observed historical sequences and one explicitly named `research_projected_sequence`; require the former for any operational forecast endpoint.

## Revised verdict

The new commit should be credited as a good audit response. It fixes the most obvious implementation defects and improves honesty about the model's status and limitations.

The remaining blocker is **evaluation alignment**: the canonical future-window dataset, the trained artifact, the validator, and the committed scorecard are not yet one coherent experiment. Until the scorecard is regenerated from a clean, timestamped, station-aware, untouched future test set, the reported numbers should be treated as exploratory diagnostics rather than validated forecast performance.
